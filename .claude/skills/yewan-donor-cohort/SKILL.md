# 野灣捐款人 Cohort 分析

## 這個 Skill 要幫誰、解決什麼
- **使用者**：野灣公益勸募科（不是資料分析師）。
- **時刻**：每月寄信/扣款失敗通知前，要決定「這個月先聯絡誰、說什麼」。
- **三個任務**（官方任務卡，各組選一個主要任務）：
  - 任務一：看懂誰在支持野灣（主要用 ①②③）——本 Skill 提供輕量輪廓與 25 歲以下比例。
  - 任務二：留住定期定額捐款人（主要用 ②④）——最常在第幾期停止？哪些是被動流失、可以救回？誰先提醒？
  - 任務三：找出讓人開始支持的時刻（主要用 ②③⑤）——哪些事件帶來新捐款人？之後有沒有再捐、轉定期？找不到原因的高峰？

> 核心原則：**先驗證、再下結論**。每一個數字都要附上樣本數與可信度判定；
> 判定為「不宜下結論」的差異，**不可以**寫成洞察或建議。

## 官方資料結構（野灣_示範資料_v1.xlsx，全部虛構）
主辦方說明頁：https://datadotgo.github.io/connect-the-dots-web/yewan_data.html（數字以此頁為對帳基準）。
| 分頁 | 粒度 | 重點欄位 | 陷阱 |
|---|---|---|---|
| ①聯絡人 | 一人一列（含沒捐款的人） | 系統編號、年齡、性別、鄉鎮市區、聯絡人建立日期 | 系統編號有 1 筆重複；年齡過半「未填寫」；沒有縣市、東區/中正區等同名 |
| ②一年內定期定額紀錄 | 每次成功扣款一列（2025/11/1–2026/10/31） | 捐款編號（主鍵）、捐款建立日期（**文字**）、總金額、交易編號、定期捐款編號 | 交易編號＝「方案第一筆捐款編號_第幾期」，**不是唯一鍵**；後段就是期數 |
| ③一年內單筆捐款紀錄 | 每筆單筆一列 | 捐款編號、捐款建立日期（日期格式）、總金額、付款工具 | **沒有捐款管道／來源欄**；有幾筆特別大的金額 |
| ④定期定額明細 | **一人一列**（11/1 匯出） | 定期定額狀態、「執行期數 / 約定總期數」、「成功次數/ 請款次數」、開始/結束/失敗或取消/最近失敗日期 | 有多個方案的人只看得到其中一個，**常常是舊方案**；合併欄位要拆；「不限」＝沒約定期數 |
| ⑤活動時間軸（虛構） | 一事件一列，表頭在第 3 列 | 日期、活動或事件、類型、管道、備註 | 「每月第一週」不是日期；有些高峰在這裡找不到原因 |

狀態定義（主辦方解讀）：待處理＝第一次扣款沒成功；暫停中＝扣款一段時間後停下來，原因不明；已失敗、已取消、已完成、進行中。

## 工作流程（照順序做，不要跳步）

### Step 0：確認情境
1. 讀 `knowledge_base/` 中的野灣背景：
   - `組織概況.md`：使命、規模，以及公益勸募課只有 2 人（說明問題時用）
   - `募款與溝通管道.md`：定期定額佔募款收入 45.7%、捐款頁規則、**換卡＝新方案**
   - `名詞對照.md`：模擬欄位和真實系統的差異（回答「還缺什麼資料」時用）
   - `捐款人溝通範例.md`：寫信件草稿時用
2. 問清楚使用者這次要回答哪個任務；需要的是「報告」、「名單」，還是「簡報素材」。

### Step 1：跑分析管線（不要自己臨時寫 pandas）
```bash
python scripts/yewan_cohort.py --data 野灣_示範資料_v1.xlsx --output-dir yewan_output
```
- `--data` 可以直接給官方 xlsx（會自動轉成 CSV 放在 `yewan_output/raw/`），也可以給已經有 5 個 CSV 的資料夾。
- 資料在 Google Drive 上時：`python scripts/fetch_sheet.py --drive-id <檔案ID> --out-dir data`，再用 `--data data`。
- 需要 pandas、numpy、openpyxl（Colab、Claude 程式執行環境都已內建）。
- 欄位名稱不同時，在 `scripts/yewan_cohort.py` 的 `COLUMN_ALIASES` 加別名；「A / B」合併欄位會自動拆開。
- 觀察截止日預設是資料中最後一筆捐款日（2026-10-31），可以用 `--as-of` 覆寫。

### Step 2：先讀資料品質，再讀結果
打開 `00_資料品質檢查.csv`，或看 `summary.json` 的「資料品質」：
- **ERROR**：停下來告訴使用者，先修資料。
- **WARN**：分析可以繼續，但要在結論裡說明影響。官方資料預期會出現的 WARN 與處理方式見 `references/data_quality_known_issues.md`。

### Step 3：跑驗證測試
```bash
python scripts/test_yewan_cohort.py --data 野灣_示範資料_v1.xlsx
```
A 組用官方格式的手工小資料檢查定義（含換卡、首期失敗、④ 沒列的方案）；B 組只用 Python 標準函式庫獨立重算關鍵數字並對帳。**有任何測試失敗，就不要交付結果。**

### Step 4：解讀結果（以 `summary.json` 為準）
- 只從 `summary.json` 和輸出的 CSV 引用數字，**不要心算、不要估計**。
- 每個發現都要對照「判定」欄位：
  - `差異顯著`／`顯著增加`：可以寫成洞察，但要附上比率、95% 信賴區間和樣本數。
  - `無顯著差異：不宜下結論`：要明確寫出「資料不支持這個差異」——例如「年齡不影響流失，所以不必分齡寫信」。
  - `未校正才顯著：不宜下結論`：一次比很多活動，總會有一個碰巧顯著；不要拿來當結論。
  - `樣本太少：不宜下結論`：寫出需要補多少資料才能判斷。
- 各指標的算法定義見 `references/metrics.md`。使用者問「這個數字怎麼算的」時，引用那份文件。

### Step 5：轉成行動
依 `references/analysis_playbook.md` 的對照表，把結果轉成「給誰 → 什麼時候 → 說什麼」。
- 任務二的主要產出是 `t2_優先提醒名單.csv`：**一人一列**，每列有「建議行動」和「理由」，已排除「另有方案正在扣款」的人。
- 任務三：看 `t3_活動前後.csv`（新捐款人與新定期方案兩個指標）和 `t3_未解釋高峰.csv`。顯示「（找不到）」的高峰＝建議勸募科回想當天發生什麼，並開始記錄。

### Step 6：交付
- **互動報告**：`report.html`（表格可排序/篩選、圖表可 hover）。
- **三頁簡報**：用 `references/analysis_playbook.md` 最後的簡報骨架。
- **行銷名單**：`t2_優先提醒名單.csv`，可匯入 Google Sheets。

每次交付都必須回答（官方「展示時請回答」）：
1. 誰、在什麼時刻會打開它？
2. 用之前和用之後，差在哪裡？
3. 還缺什麼資料？誰來補？怎麼持續下去？

## 不可以做的事
- **不可以直接用 ④ 的狀態做名單或算流失**。④ 一人一列，常是換卡／續約前的舊方案，或同時兩個方案中的一個；要用 `03_定期方案主檔.csv`（由 ② 定期捐款編號還原），並看 `此人仍有其他方案在扣款`。
- 不可以把「方案停止」等同「捐款人流失」。同一人另有方案在扣款＝`換方案(非流失)`，不要打擾。
- 不可以把 `交易編號` 當主鍵（會重複），主鍵是 `捐款編號`；期數取交易編號後段。
- 不可以合併 ② ③ 前忘記統一日期格式（② 是文字、③ 是日期）。
- 不可以拿「年齡未填寫」當一個年齡層去算 25 歲以下比例；分母用已填年齡者，並附上填寫率。
- 不可以用鄉鎮市區直接推縣市（東區、北區、中正區…跨縣市同名）。
- 不可以宣稱知道捐款「從哪個管道來」——③ 沒有來源欄位，只能用「首捐日期落在哪個活動窗」推測，而且要看判定欄位。
- 不可以把 `狀態=已完成` 當成「續約了」；要看此人有沒有其他方案在扣款。
- 不可以把 Cohort 熱圖中的空白格當成 0，空白代表還無法觀察。
- 不可以把 `活動時間軸` 寫成野灣的真實活動，它是虛構示意；整份資料也都是虛構的。
- 不可以因為「看起來有差」就下結論，一定要看判定欄位。
- 不可以編造動物故事或組織數字。撰寫信件或簡報時，只能引用 `knowledge_base/` 和年報中的內容。
