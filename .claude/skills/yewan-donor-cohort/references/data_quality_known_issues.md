# 已知資料問題（2026-11-15 用官方資料 野灣_示範資料_v1.xlsx 檢查）

官方資料說明頁：https://datadotgo.github.io/connect-the-dots-web/yewan_data.html 。頁面公布的筆數、人數、狀態分布、空白率、每月成功扣款人數，`test_matches_official_data_page` 都會逐一對帳。

資料全部虛構，期間 2025-11-01 ~ 2026-10-31，規模約為真實資料的一半。以下問題都會由 `validate()` 自動偵測；拿到新資料時，以最新的 `00_資料品質檢查.csv` 為準。

## 結構面：大致乾淨（沒有 ERROR）
- ②③ 的 `捐款編號` 沒有重複、兩表也不重疊；②③④ 的 `系統編號` 全都對得到聯絡人。
- ② 的每個 `定期捐款編號` 只屬於一個人；期數（交易編號後段）隨日期遞增、沒有跳號。
- ② 扣款金額全部等於 ④ 約定金額；④ 執行期數＝成功次數；剩餘期數＝約定總期數 − 執行期數。

## 業務規則造成的解讀陷阱
- **換卡＝新方案**：捐款人換信用卡要重新設定定期定額（官網 FAQ）。資料上就是「舊方案已失敗／待處理 + 新方案進行中」。④ 的 258 個「待處理」全部屬於此人另有方案在扣款的情況——第一次扣款失敗後，捐款人多半自己重新設定了。
- **不限期＝持續扣款**：「執行期數 / 約定總期數」中的「不限」是官網預設，不是缺漏。
- **已完成 ≠ 續約**：期滿的方案要看此人有沒有其他方案在扣款，才知道有沒有續約。
- **捐款頁沒有來源欄位**：③ 只有付款工具，無法直接歸因到活動；只能用「首捐日期落在活動窗」推測。

## 給 NGO 的資料補強建議
1. ④ 匯出時改成**一個方案一列**（而不是一人一列），並保留每個方案的狀態與失敗原因代碼。
2. 取消／變更表單的紀錄（原因：換卡、經濟因素、不滿意……），才能確認「換方案」。
3. 捐款頁加 **UTM／活動專屬連結**，才能把捐款歸因到活動。
4. 活動時間軸持續記錄（含社群貼文、媒體曝光），尤其是找不到原因的高峰當天。
5. 寄信與開信紀錄，才能衡量「提醒」本身的成效（A/B 測試）。
